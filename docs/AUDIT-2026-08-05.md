# Codebase Audit — 2026-08-05

Branch `chore/dead-code-audit` @ `a96bf26`. Next.js 16.2.12 / React 19.2.4 /
Prisma 7.8 / PostgreSQL. 213 tracked files, ~13k lines of application source.

**Verdict: the build is green and the plumbing is sound, but the money path is
not safe to run in production.** Four defects let a customer set their own
order total or mint inventory. They are all in one 150-line region of
`src/server/store.ts` and all fixable in a day.

The second-largest cluster is not a bug class but a pattern: **half-built
features whose admin controls write columns nothing reads.** Coupon `isActive`,
landing-page `published`, saved addresses, product variants, per-product order
limits, and email verification are all wired at one end only. §4 lists forty.

Method: two rounds of parallel audit agents, one per lens, across eight lenses —
auth/security, data layer, commerce correctness, validation/error handling,
documentation, frontend/backend contract, dead code, build/CI/ops. All eight
completed. Findings in §2, §3 and §6 were adversarially verified by a second
agent and the significant ones re-read by hand against the source; §4 was
adversarially verified. §5, §7 and §8 were not verified — §9 says exactly what
that leaves open.

## 2. Critical — money and inventory

All four verified by hand. All four are reachable by an ordinary customer.

### C1 · Negative quantity sets the customer's own total and mints stock

`src/app/actions.ts:73` → `src/server/store.ts:1226` → `store.ts:1547`

```ts
const quantity = asNumber(formData.get("quantity"), 1);   // actions.ts:73
```

`asNumber` (`src/lib/utils.ts`) only rejects non-finite values — `-5` passes.
Nothing downstream clamps it:

* `addToCart` writes `quantity: existing.quantity + quantity` (`store.ts:1251`) with no guard.
* `createOrderFromCart` computes `subtotal += item.product.price * item.quantity` (`store.ts:1554`) → negative subtotal.
* The stock guard is `if (item.product.stock < item.quantity)` (`store.ts:1551`) → `10 < -5` is false, so it passes.
* The decrement is `nextStock = product.stock - item.quantity` (`store.ts:1609`) → **stock increases**.

A crafted POST to the server action produces an order with a negative total and
a product whose stock went up. Server actions accept arbitrary `FormData`; the
`min` attribute on the input is decoration.

**Fix:** clamp once, at the boundary in `addToCart`:
`quantity = Math.max(1, Math.trunc(quantity))`. Same in `updateCartQuantity`
(`store.ts:1323`, which clamps the lower bound but not to an integer).

### C2 · Deactivated coupons still discount — the admin toggle does nothing

`src/server/store.ts:1544` vs `src/app/admin/coupons/page.tsx:47`

```ts
const coupon = couponCode ? await tx.coupon.findUnique({ where: { code: couponCode } }) : null;
```

`coupon.isActive` is never read. The admin UI has an explicit Active/Hidden
`<select name="isActive">` and renders a `StatusPill` for it; `saveCouponAction`
persists it. Deactivating a leaked promo code in the admin panel changes the
badge and nothing else — customers keep redeeming it forever. This is the
cleanest frontend/backend gap in the codebase: a control that writes a column
no reader consults.

**Fix:** `where: { code: couponCode, isActive: true }`.

### C3 · Coupon discount is unbounded — negative order totals

`src/server/store.ts:1557`

```ts
const discountAmount =
  coupon && subtotal >= coupon.minOrderAmount
    ? coupon.type === "percentage"
      ? Math.round((subtotal * coupon.value) / 100)
      : coupon.value
    : 0;
const deliveryCharge = getDeliveryChargeForZone(settings, deliveryZone, subtotal - discountAmount);
const total = subtotal - discountAmount + deliveryCharge;
```

`saveCouponAction` (`admin/actions.ts:485`) reads `value` with `asNumber` and
validates nothing. A fixed coupon worth more than the cart, or a percentage
above 100, yields a negative `discountAmount`-adjusted total, which is then fed
to the free-delivery threshold comparison. A typo in the admin form — `1000`
instead of `10` — is enough.

**Fix:** clamp at the point of use — `Math.min(subtotal, computed)` — and
validate `value` in `saveCouponAction` (`1..100` for percentage, `> 0` for fixed).

### C4 · Stock oversell: read-then-write under READ COMMITTED

`src/server/store.ts:1607-1613`, and identically in `reserveOrderInventory`
(1450), `releaseOrderInventory` (1482), `setProductStock` (560)

```ts
const nextStock = product.stock - item.quantity;
await tx.product.update({ where: { id: item.productId }, data: { stock: nextStock } });
```

The check and the write are separate statements and the write is an **absolute
value**, not a delta. Prisma's interactive `$transaction` runs at PostgreSQL's
default READ COMMITTED with no row lock taken. Two simultaneous checkouts of the
last unit both read `stock = 1`, both pass the guard, and both write the literal
`0`. Two units sold, one exists, and `inventory_logs` records two rows each
claiming `oldStock: 1, newStock: 0`, so the discrepancy is invisible.

**Fix:** make the check and the write one statement.

```ts
const { count } = await tx.product.updateMany({
  where: { id: item.productId, stock: { gte: item.quantity } },
  data: { stock: { decrement: item.quantity } },
});
if (count !== 1) throw new Error(`Insufficient stock for ${item.product.name}`);
```

Use `{ increment }` for the release and adjust paths. No schema change.

## 3. High

Verified by hand unless marked.

### H1 · Password reset does not invalidate existing sessions

`src/app/actions.ts:591-601`. `resetPasswordAction` consumes the token and calls
`updateUserPassword`, then returns. Sessions live in the `sessions` table keyed
by `tokenHash`; none are deleted. A stolen session cookie survives the reset the
victim performed *because* of the theft — the one action a compromised user
takes to lock the attacker out does not.

**Fix:** `await prisma.session.deleteMany({ where: { userId: user.id } })`
alongside the password write. The same call also closes the outstanding
duplicate reset tokens (`auth.ts:227` deletes only the one consumed).

### H2 · Order records are orphaned from the customer's account

`prisma/schema.prisma:196` declares `customerId String?` with a `User` relation
at :219. The `order.create` in `createOrderFromCart` (`store.ts:1569-1598`)
never sets it. Every order placed through the storefront — signed in or not —
has `customerId = NULL`. Order history in `/account` cannot be built from a
column nothing writes.

**Fix:** pass the session user into `createOrderFromCart` and set
`customerId: user?.id ?? null`.

### H3 · Password reset is silently dead when SMTP is unconfigured

`src/server/email.ts:124`

```ts
if (!smtpHost || !smtpPort || !smtpUser || !smtpPass) {
  console.warn("SMTP not configured; email would be sent to:", to, template.subject);
  return { success: true };
}
```

Returning `success: true` for an email that was never sent is a lie to every
caller. `forgotPasswordAction` checks `emailResult.success` (`actions.ts:562`),
sees true, and tells the user "a reset link has been sent." Combined with the
next finding, a production box missing SMTP credentials has a completely
non-functional, completely silent password reset.

**Fix:** return `{ success: false, error: "SMTP is not configured" }`. Keep the
console warning. Let the caller decide.

### H4 · `.env.local` silently points migrations at a hardcoded fallback database

`README.md:42` instructs `Copy-Item .env.example .env.local`. Next.js loads
`.env.local`, so `npm run dev` works — but `prisma.config.ts` starts with
`import "dotenv/config"`, which loads **`.env` only**, and then:

```ts
const fallbackDatabaseUrl = "postgresql://postgres:postgres@127.0.0.1:5432/ecommerce";
const generateDatabaseUrl = process.env.DATABASE_URL?.trim() || fallbackDatabaseUrl;
```

A developer who follows the README exactly gets a working dev server and has
`prisma migrate` / `prisma:seed` / `db:reset` silently target a different
database than the app. A destructive command aimed at the wrong database, with
no error, is the failure mode here.

**Fix:** README should say `.env` (matching `.env.example` and every script), or
`prisma.config.ts` should load `.env.local` too. Drop the silent fallback URL —
fail loudly on a missing `DATABASE_URL`.

### H5 · `OPERATIONS.md` states a bKash safety property the code does not have

`docs/OPERATIONS.md:51` — "bKash stays disabled unless every provider credential
and `BKASH_WEBHOOK_SECRET` …". `src/server/integration-config.ts:50`:

```ts
webhookSecret: process.env.BKASH_WEBHOOK_SECRET?.trim() || appSecret,
```

It falls back to `appSecret`. The callback route's `if (!secret)` guard
(`callback/route.ts:31`) therefore never fires, and callbacks are verified
against a secret bKash was never given. An operator reading the runbook believes
an unset variable is a safety interlock; it is not.

### H6 · `confirmPayment` writes three tables with no transaction

`src/server/integrations.ts:205-224`. `upsertPayment`, `addPaymentLog` and
`updateOrderPayment` are three independent top-level awaits (the third opens its
*own* transaction). A restart or dropped connection between them leaves
`payments.status = 'paid'` while `orders.paymentStatus` stays `'pending'`. The
customer has paid; the order is never fulfilled; nothing reconciles.

**Fix:** wrap all three in one `prisma.$transaction`, keeping the outbound HTTP
call in `initiateBkashPayment` outside it.

### H7 · Payment callbacks have no status state machine

`src/server/integrations.ts:199`. Replay protection exists and works — a
fingerprint over `{paymentId, orderId, provider, transactionId, status,
payload}` (`security.ts:186`) short-circuits an identical repeat. But the
fingerprint **includes the status**, so a replayed callback carrying a
*different* status hashes differently and is applied. A `cancelled` callback
arriving after `paid` un-pays a paid order. There is no legal-transition table.

**Fix:** reject transitions out of `paid` except to `refunded`, in
`confirmPayment` before the write.

### H8 · `recordAuditLog` escapes the transaction it is called from

`src/server/audit.ts:17` calls `getPrisma()` and takes no
`Prisma.TransactionClient`. It is invoked from inside eleven interactive
transactions (`store.ts:581, 859, 918, 947, 981, 1257, 1640, 1762, 1827, 1875,
1904`). Two consequences: audit rows commit on a separate connection and survive
a rollback of the operation they describe, and every mutation holds two pooled
connections instead of one — with `pg`'s default `max: 10`, ten concurrent
mutations can deadlock the pool until Prisma's transaction timeout fires.

**Fix:** add an optional `client` parameter, `const prisma = input.client ??
getPrisma()`, and pass `tx` at all eleven sites — `tx` is already in scope at
every one.

### H9 · Free-text district silently decides shipping cost and COD eligibility

`src/components/checkout-form.tsx:65` renders District as a free-text `Field`
with placeholder "Dhaka". `deriveDeliveryZone` (`store.ts:1410`) then
substring-matches it:

```ts
if (normalized.includes("dhaka city") || normalized === "dhaka") return "inside_dhaka";
if (normalized.includes("dhaka")) return "sub_dhaka";
return "outside_dhaka";
```

"Gazipur" — squarely sub-Dhaka — bills as outside-Dhaka. A typo (`"dhka"`) does
the same. Worse, zone also gates payment: `assertPaymentMethodAvailable`
(`store.ts:1425`) throws "COD is not enabled for this delivery zone", which
`checkoutAction`'s catch (`actions.ts:524`) flattens to "Something went wrong.
Please try again." A customer who mistypes their district is blocked from
checkout with no way to learn why.

**Fix:** make District a `<select>` over `domain.ts`'s zone list (it already
defines all three with names and descriptions) and drop the string matching.

### H10 · No index on any foreign key or sort column

`prisma/schema.prisma` contains exactly two `@@index` declarations, both on
`Address` (:427-428). PostgreSQL does not create indexes for foreign keys
automatically. Unindexed and queried on every request: `CartItem.cartId`,
`OrderItem.orderId`, `Order.customerId`, `Payment.orderId`,
`OrderStatusHistory.orderId`, `InventoryLog.productId`, `Product.categoryId`,
`Product.brandId`. Fine at 51 seeded products; sequential scans on every cart
read at real volume.

### H11 · Checkout writes unvalidated customer data

`src/app/actions.ts:441-445` reads `customerName`, `customerPhone`, `district`
and `shippingAddress` with `asString` and passes them straight to
`createOrderFromCart`. No zod schema, no non-empty check. The admin path
`createManualOrder` (`store.ts:1673-1676`) *does* validate all three — the
customer-facing path is the less-defended one.

### H12 · `registerAction` throws instead of returning form state

`src/app/actions.ts:157` (unverified — agent finding, code location confirmed).
A duplicate-email registration throws into the error boundary rather than
rendering a field error. Same shape reported for admin form actions
(`admin/actions.ts:66`) destroying the whole product form on a validation
failure.

## 4. Frontend ↔ backend gaps

40 findings, every one adversarially verified. This is the largest defect
cluster in the codebase and the dominant theme is consistent: **the admin UI
writes columns that no reader consults, and the storefront renders affordances
the backend does not honour.** Coupon `isActive` (C2) was the first instance
found; it is not the only one.

### F1 · `/account/profile` cannot be edited at all

`src/components/profile-form.tsx:28-53`. All three fields pass `value` with no
`onChange`:

```tsx
<Field label="Full name" name="name" required value={state.name ?? initialData.name} autoComplete="name" />
```

`Field` spreads `...rest` straight onto `<input>` (`ui/field.tsx:49-55`) and the
file is `"use client"`, so React treats these as controlled inputs and reverts
every keystroke. The page is reachable from the "Edit profile" button on
`account/page.tsx:26`, and can only ever resubmit the values it loaded.
`login-form.tsx` and `checkout-form.tsx:47-48` pair `value` with `onChange`
correctly — this file did not.

**Fix:** `defaultValue` instead of `value` on all three. `address-form.tsx`
already uses that pattern.

### F2 · Saved addresses are write-only

`/account/addresses` (shipped in `a8e6697`) creates, edits, defaults and deletes
addresses. `src/app/checkout/page.tsx` imports nothing address-related, and
`checkout-form.tsx` offers a single free-text `shippingAddress` textarea. The one
screen where a saved address is worth having never reads them. The addresses
page's own copy promises they will speed up checkout.

### F3 · Draft landing pages are publicly served

`store.ts:2002` — `prisma.landingPage.findUnique({ where: { slug } })`, no
`published` filter. `l/[slug]/page.tsx:22` only checks `if (!landingPage)
notFound()`. The admin form writes `published: asString(formData.get("published"))
=== "on"`. Same shape as C2: a published/draft toggle whose column nothing reads.
Anyone with the slug reads the draft.

### F4 · The landing-page builder can never create a second page

`admin/landing-pages/page.tsx:17` — `const selected = pages.find((item) =>
item.id === edit) ?? pages[0];`. The hidden `<input name="id" value={selected?.id
?? ""}>` is therefore always populated once one page exists, and
`saveLandingPageAction` passes `id: asString(...) || undefined` into
`upsertLandingPage`, which always takes the update branch. There is no "New page"
affordance. The builder is create-once, then edit-forever.

### F5 · Both payment methods always render, even when disabled

`checkout/page.tsx:24` computes `paymentsAvailable` and uses it only for a
decorative `StatusPill` at :36. `CheckoutForm` receives no gating prop and
hardcodes both radios (`checkout-form.tsx:139, :157`), defaulting to `"cod"`.
With `codEnabled = false`, every submit dies in `assertPaymentMethodAvailable`
and is flattened to "Something went wrong." The page's own copy at :90 claims
disabled methods are rejected — they are, but they are also the only options
offered.

### F6 · Cart and checkout price delivery from the *store's* address

`checkout/page.tsx:21` and `cart/page.tsx:18`:

```ts
const deliveryZone = deriveDeliveryZone(settings.address ?? "Dhaka");
```

The order is priced from `deriveDeliveryZone(input.district)` — the *customer's*
district (`store.ts:1539`). The two never agree except by coincidence. The seeded
store address "Dhanmondi, Dhaka, Bangladesh" derives `sub_dhaka` (৳100); a
customer in Chattogram is quoted that and charged `outside_dhaka` (৳130). The
figure is labelled "Estimated total", which is the only reason this is High and
not Critical. Neither page has the district at render time, so neither can price
it correctly — the fee row should move into `CheckoutForm` where the district
input lives, or be dropped.

### F7 · bKash cancellation strands the customer

`payments/[provider]/cancelled/page.tsx:19-30` offers "Try again" → `/checkout`
and "Back to cart". Both are empty: `createOrderFromCart` runs *before*
`initiateBkashPayment` (`actions.ts:494` then `:512`) and ends with
`tx.cartItem.deleteMany` (`store.ts:1634`). The page's `searchParams` type is
`{ paymentId?: string }` only, so it cannot even link to the pending order it
just created. Both recovery paths are dead ends.

### F8 · Homepage add-to-cart is gated on demo slugs

`product-section.tsx:13`:

```ts
collection.slug === "cotton-unstitched" || collection.slug === "premium-silk-saree" || collection.slug === "1piece-dresses"
  ? "Add to Cart" : "Select Options"
```

Three seed slugs, hardcoded. Every real store's categories fall through to
"Select Options", which routes to a product page with no options to select
(`storefront-card.tsx:19`).

The project is not under-documented — it is **over-documented and contradicted**.
Eleven markdown files, ~130 KB, most of them dated snapshots of finished work,
several stating things the code no longer does.

**Factually wrong, and dangerous:** H4 (`.env.local`) and H5 (bKash secret)

`edge.zatiqeasy.com` and the ExonHost DNS-zone ticket is unresolved. It is the

Only `docs/OPERATIONS.md` was already maintained.

**Genuinely missing, with a concrete cost:**

* The bKash callback wire contract — field names, `x-signature` derivation, expected status values — is documented nowhere. The integration cannot be brought up from the docs alone; you have to read `callback/route.ts` and `integrations.ts`.
* No architecture note. A new reader has no map to the fact that `store.ts` is the entire data layer, that `src/server/*` is server-only, or that every mutation is a server action rather than an API route.
* `E2E_VISUAL` and `E2E_ALLOW_REMOTE_ORDER` are read by the Playwright suite and documented only in source comments; the suite also needs a seeded demo admin no documented command produces.
* `src/lib/product-import.ts` — 452 lines, a hand-rolled RFC4180 parser, zero comments, zero tests. `docs/DEAD_CODE_CLEANUP_PLAN.md` already flags this as an open item.

**Recommendation:** delete or move to `docs/archive/` the seven dated reports.
Being wrong is worse than being absent, and their volume hides
`OPERATIONS.md`, which is the one document that matters.

## 6. Build, CI/CD and operations

19 findings, adversarially verified.

**The pre-migration and pre-wipe backups can be empty and the scripts continue.**
`scripts/apply-production-migration.ps1:347`:

```powershell
-Command "$loadEnv && pg_dump `"`$PSQL_URL`" | gzip -9 > $dumpPath && ls -l $dumpPath"
```

The guard `Assert-RemoteSuccess -Output $output -What "pg_dump"` exists, but a
shell pipeline exits with the status of its *last* command. `gzip` succeeds on
truncated or empty input, `ls -l` then succeeds, and the assertion sees exit 0.
There is no `set -o pipefail`. The one safety net before a production migration
or a database wipe can be a valid gzip of nothing. **Fix: `set -o pipefail`, and
assert a minimum byte count on the dump.**

Also confirmed:

* **The Linux release bundle is built on Windows.** `deploy-production.yml:16` runs `windows-latest`, so `npm ci` installs win32 `sharp` and the bundle ships a binary the cPanel host cannot load.
* **Nothing checks that `prisma/migrations` reproduces `schema.prisma`** — no `migrate diff` in CI. This exact drift already reached `main` once (`7a76df3`).
* **The 13 integration tests skip on developer machines too**, not just CI: `vitest.config.ts:13` never loads `.env`, so `hasDatabase` is false locally unless `DATABASE_URL` is already exported.
* **`e2e/` is excluded from the TypeScript program** (`tsconfig.json:25`) and from every workflow — the only tests covering checkout money and admin authorization are neither run nor typechecked.
* **Production `/api/health/ready` is permanently shadowed by a `ready.php`** written by `deploy-cpanel.ps1:589`, so readiness cannot detect a dead Node app. The `next.config.mjs:4` rewrite for the same path is separately dead, shadowed by the real route handler.
* **The deploy runs lint and build but never the tests**, and `workflow_dispatch` can ship any ref with no green-CI requirement.
* **Release extraction overwrites the live app root in place** — no atomic swap, no previous release to roll back to.
* **The deploy's forensic log is written only on success**, and in Actions to a discarded runner workspace.
* **Two `e2e/storefront.spec.ts` tests assert nothing about the behaviour their names claim** and would pass if that behaviour were deleted.
* No security headers anywhere — no `headers()` in `next.config.mjs`, no middleware, so no CSP, HSTS, `X-Frame-Options` or `X-Content-Type-Options`.
* Six `console.*` calls in all of `src/`, no instrumentation hook, no documented log destination under Passenger.
* No `engines` field pinning Node outside CI. `Dockerfile` is built by nothing and starts a different server than production does.

One finding was **rejected** by the verifier: the claim that
`patch-standalone-server.mjs` can silently no-op against a future Next version —

## 9. Accessibility, SEO, i18n, performance

Run by hand after the agent budget ran out. Two clean results and one large gap.

### Accessibility — clean, and better than the rest of the codebase

`src/components/ui/field.tsx` wires `label`/`hint`/`error` to the control through
generated ids, sets `aria-invalid`, and puts `role="alert"` on the error node.
`use-overlay.ts` implements a real focus trap, Escape-to-close, and focus
restoration to the opening element, with a comment explaining why. `drawer.tsx`
carries `role="dialog"`, `aria-modal`, `aria-labelledby`, `aria-describedby`.
Fourteen `role="alert"` / `role="status"` regions across the components.

The primitive layer the responsive work introduced is sound. **The one
accessibility defect found is F1** — frozen profile inputs are also an
accessibility failure, not just a usability one.

This also means §7's suggestion to replace `useOverlay` with `<dialog
showModal>` should be **rejected**: the hand-rolled version is correct,
documented, and already load-bearing. Swapping it is churn, not simplification.

### SEO — the largest untouched gap in the project

This is a commerce site with essentially no search presence, and no lens had
looked.

* **One `metadata` export in the entire app** — `src/app/layout.tsx`. 36 `page.tsx` files; 35 have none.
* **`/product/[slug]` has no `generateMetadata`.** Every product page shares the title "Bornohin" and one generic description. No product is distinguishable in a search result or a shared link.
* **No `sitemap.ts`, no `robots.ts`**, no manifest, no `opengraph-image`.
* **No canonical URLs**, so `/shop?category=x` and its variants compete with each other.
* **No product structured data.** No JSON-LD `Product`/`Offer`, which is what produces price and availability in Google results — the single highest-value SEO item for a shop.
* Root `metadata` has no `metadataBase`, so any Open Graph image added later resolves relatively and breaks.

The fix is small and mechanical: `generateMetadata` on `/product/[slug]`,
`/shop`, `/l/[slug]` and the content pages; a `sitemap.ts` driven by
`listProducts()`; a `robots.ts`; a JSON-LD block on the product page. Perhaps
150 lines total, against a direct revenue effect.

### Performance

* **No pagination anywhere.** `take:` and `skip:` appear **zero** times in `store.ts`. `listProducts()` returns every product; every admin list loads its whole table. This corroborates the data-layer finding and compounds with H10 (no indexes).
* `site-header.tsx` is 609 lines and `"use client"` — the largest component in the app, in the bundle on every route.
* Clean: no raw `<img>` anywhere (`next/image` in 7 files), and `lucide-react` imports are named, so tree-shaking works. Neither is a problem.

### i18n

`money()` centralises BDT through `Intl.NumberFormat("en-BD")` — consistent.
The real issue is already recorded in §8: `slugify()` strips all non-ASCII, so a
Bengali product name yields an empty slug and collides on the second one.
